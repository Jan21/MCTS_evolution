Overview

The north star. Build a complete AlphaZero-style self-play loop for Ricochet Robots planning that ends up beating every supervised planner in this repository — the forward move-level planner and the backward subgoal planner — on the one metric that matters: realized primitive moves from the initial state to the terminal state, on a fixed benchmark, under a fixed search budget. Fewer moves wins. Secondary: solve rate (a planner that solves fewer puzzles does not get to brag about the ones it solved); compute per puzzle is the tiebreaker. PROBLEM.md §1

The supervised campaign proved the pieces exist: a size-free value net that writes near-optimal labels, planners that train to useful strength from those labels, and a full NN-only data pipeline that matches the exact-solver pipeline. What no one has done is close the loop: let the network search, learn from its own search, and iterate past the ceiling of its teacher.

The game, in five lines

  • An n×n grid with interior walls; R robots on distinct cells.
  • A primitive move picks a robot and a direction; it slides until blocked by a wall or another robot (it must slide at least one cell).
  • An instance fixes a board, robot starts, a target robot and a target cell; terminal = target robot on target cell.
  • Cost = number of primitive moves. Non-target (“helper”) robots matter: optimal play routinely parks them as blockers.
  • Deterministic MDP, discount 1; ground truth (exact solver) exists only for n ≤ 64 — validity is checkable at any size by physics replay, optimality only ≤ 64.

The loop

Iteration k (PROBLEM.md §5): generate fresh instances on fresh lean boards → search with net k under a fixed expansion budget → certify → append to buffer → train net k+1 (warm-start from k, CollapseStop armed) → gate: bench vs net k AND vs the frozen supervised baselines → promote or diagnose.

The AlphaZero mapping

AlphaZero piecehere
Game rulessimulate.py physics + lean boards (self-generated positions at will)
Network f(s) → (p, v)policy over the chosen action space + value = cost-to-go estimate (§6.2)
MCTS with PUCTover subgoal decisions (recommended) or primitive moves (§6.1); "win" is replaced by realized move count → minimize cost, so back up negative realized cost (or a cost-bucket distributional value like the existing HL-Gauss value nets)
Self-play gamessolve generated instances with search; certify every solution by replay; realized primitive count is the episode's ground truth
Training targetspolicy ← visit distribution at each decision; value ← realized cost-to-go from each visited state (certified labels only — exactly the descent labeler's contract, now with search instead of greed)
Replay bufferrolling window over recent iterations' certified episodes; keep board/instance provenance for leakage control
Evaluator / gatingpinned bench arena (§7) + fidelity gauge (§4.1) + seed-noise-aware promotion (§4.7)

Quoted from PROBLEM.md §5. This is the only table on the page that is not read from a result file — it is the design, not a measurement.

The improvement hypothesis, stated honestly: greedy descent under the labeler already labels at 86–93% argmin agreement, and MCTS at inference found solutions greedy descent misses. If search-labeled data trains a net that searches better, the loop climbs. If it merely matches the supervised ceiling, that is a publishable negative result about self-play in deterministic single-agent planning — and per §4.3 the loop can also go down, which is what the fidelity gauge is for. §6.1 — action space
Subgoal MCTS (recommended) vs primitive-move MCTS.		Recommendation: subgoal decisions — (a) horizon 2–6 vs 8–30 makes search tractable per expansion budget; (b) the strongest baseline lives there, so the bootstrap is warm; (c) realization + certification machinery already exists (descent.py, eval/realize.py); (d) the backward planner beats forward by growing margins with scale (+47.8 pts solve at 32×32). Columns: solve rate = aggregate.solved/aggregate.n and aggregate.solve_rate; mean realized moves = aggregate.mean_moves (identical to mean_realized_strict for backward systems — playable moves after physics replay); mean regret = aggregate.mean_regret; % optimal = aggregate.pct_optimal; mean expansions / mean s/inst = aggregate.mean_expansions / mean_seconds; set is frontier when the aggregate carries d_star_placeholder or the protocol's instances file has no d_star at all (regret and optimality are then suppressed, because no optimum exists there). The exact optimum row is the mean d_star of the bench JSONL itself — the ceiling nothing can beat. Careful: a system's mean moves and mean regret average over the instances it solved, while the exact-optimum row averages the whole file, so a system that solves only the easy subset can print a mean below the file's mean d* without being better than optimal — always read mean moves next to solve rate, which is exactly why PROBLEM.md §1 makes solve rate the qualifier on the moves metric.

Reading the g32r4 pair the way PROBLEM.md §7 does: the forward planner is slower but near-optimal when it solves, the backward planner solves more and faster but further from optimal. Beating backward on moves while matching its solve rate ≈ closing toward forward's quality at backward's speed — that is the headline chart this project is aiming at.

Ceiling study — what the subgoal language can express

Why. PROBLEM.md §6.1: “the candidate generator bounds the reachable policy: if optimal play requires a subgoal the generator never proposes, no amount of search finds it. Measure the generator's ceiling early.” §11 adds why it comes first: “it's free and it bounds the project.” The supervised track's probe answered the solve-rate question on failing instances only. This one answers the question that matters for the self-play metric, on the whole pinned bench: how many primitive moves does the best plan the language can express cost, versus the exact optimum d*?

How. self_play_robots/spr/ceiling.py runs an exhaustive best-first search over partial plans in abstract plan-cost order (the solver's own admissible ordering — no network anywhere), strictly realizes every complete plan it pops (eval.realize.strict_moves, the arena's own certified move count) and records the first and the best realizable plan. best_realizable_moves is a tight upper bound on the language optimum, not a proof: a plan whose strict count undercuts its abstract cost (an incidental robot serving as a stopper) can in principle sit beyond the search bound.

What this section will say

Once the arms land, each one gets a plain-language reading of the form “the best plan the subgoal language can express costs X moves against an exact optimum of Y, and reaches the optimum on Z% of the bench”, plus the histogram of the per-instance gap. That number is a hard bound on the self-play planner in the subgoal action space: no amount of search can beat a plan the language cannot write.

What this bounds. Everything above is measured with no network anywhere — it is a property of the plan language and its candidate generator, not of any planner. In the subgoal action space the self-play planner can never beat the best-plan column on the moves metric, however good its search or its net becomes. The distance between the supervised planner's mean realized moves (Baselines) and this ceiling is the room the whole project has to play in; the distance between the ceiling and mean d* is what would require the primitive-move action space or a richer generator (PROBLEM.md §6.1).

Glossary

Definitions quoted or condensed from PROBLEM.md and the inherited FINDINGS log; where a number can be read from a file instead of asserted, it is.

playable-moves scoring
The only scoring the arena accepts: a solution counts as the number of primitive moves actually executed against the physics, after replay — not the abstract plan cost the planner thought it had. In the result JSONs this is mean_realized_strict, and mean_moves is set to it. PROBLEM.md §7.
expansion budget
The fixed search budget every arm gets, so comparisons are apples-to-apples: 1200 node expansions with k=5 candidate children per expansion, as recorded in the protocol block of supervised_valuenet/scaling/results/g24r4/comparison.json. Expansion definition recorded in the same file: one popped search node whose children are generated (= 1 policy pass + 1 batched value pass over <= k children, in both systems). Inside self-play generation you may spend more — but never in a way that biases what the data contains (§4.3, §6.5).
certification / replay
Nothing a network reports counts until it is replayed move-by-move against simulate.py physics (eval/compare.py --dump-moves + eval/replay_validate.py; spr.arena quarantines a run that fails). In the loop: a backup value from an unrealized plan is a hypothesis; only realized, replayed plans update the record. This is also the defense against the self-play analogue of reward hacking. PROBLEM.md §4.6.
subgoal / bottleneck / support / helper
The backward planner does not choose moves; it chooses subgoals — segment endpoints and helper placements — from a generated candidate set, reasoning from the goal backwards. A helper is any non-target robot; optimal play routinely parks helpers as blockers, which is exactly why a plan step may be “put the blue robot there” rather than a move. A realization step turns the subgoal plan into primitive moves and physics-verifies it. PROBLEM.md §2, §6.1.
backward vs forward planner
Two action-space views with separately trained nets. Backward / subgoal: shallow horizon (2–6 decisions), branching = candidate-set size; the strongest supervised planner and the recommended self-play main line. Forward / move-level: actions are primitive moves, deep horizon (8–30+), small branching; slower but near-optimal when it solves. Both appear in the Baselines tables, read from the same comparison files.
base / B1 / B2 vocabulary
The language a plan is written in. Base names plan steps by absolute board cells. B1 adds park repairs. B2 adds by-reference steps (“park blue where red currently stands”) — more expressive, far more expensive for the exact solver to label, and the source of the supervised track's negative result (a net distilled from iteration-capped B2 data reproduced the cap's pathology, FINDINGS 68). Vocabulary separation is absolute: base and B2 datasets never mix. This project is base-vocabulary unless the owner says otherwise (PROBLEM.md §10); the B2 rows on this page are baselines and ceiling arms, not training data.
seed noise bars
Two runs of the same arm differing only in random seed differ by ~3.4 solve / ~6.6 optimality points at g24r4 (FINDINGS 67→71); PROBLEM.md §8 turns that into the M1 gate of 3.5 solve points / 6.6 optimality points. A promotion decision inside the loop must clear this bar — or use a paired-instance test (McNemar over the per-instance solved vector). The measured spread for this repository's own files is computed live in the Baselines tab.
fidelity gauge
Argmin agreement of self-generated value targets against exact optima: at each decision, does the label pick the same best candidate as the exact solver? Cheap to measure ≤ 64. Calibrated by the supervised track: ~91% agreement → planners match exact-taught ones, ~89% keeps solve rate but loses optimality, ~82% collapses (FINDINGS 74). A slide below ~90% predicts a utility slide before the bench shows it — the loop's early-warning instrument. PROBLEM.md §4.1.
lean boards
Boards generated at any size in seconds by nn_labeler/leanboard.py (3.8 s at 96×96 vs 11.9 h for the eager path), layout-identical to eager boards (parity-proven), with a lazy distance oracle. They make “fresh instances every iteration” essentially free — which is where self-play diversity comes from in a deterministic single-agent game (§6.4).
d*
The exact move-optimal cost of an instance, from the Rust solver, stored per line in the pinned bench JSONL. Exists only for n ≤ 64 (hard engine assert), and only on the graded sets. Measured here: data/bench450.jsonl mean d* = 6.37 over 450 graded instances; g24r4/bench.solved.jsonl mean d* = 7.69 over 232 graded instances.
frontier set
The hard tail: bench.unsolved.jsonl instances that nothing had solved when the bench was pinned, so no optimum exists (d_star null or 0, and the aggregate may carry d_star_placeholder). Only solve rate and mean realized moves are meaningful there — this page suppresses regret and optimality on frontier rows rather than printing a meaningless number.
graded set
The complement: bench.solved.jsonl (and eval/data/bench450.jsonl at g16r4), where every instance carries d*, so % optimal and mean regret are defined.
node-hour (nh)
The cluster's cost unit — one full node for one hour; 1 GPU for 1 h = 0.125 nh. The whole supervised campaign cost ~27 nh; a self-play loop is more expensive by nature, which is why every milestone in PROBLEM.md §8 carries an estimate.
