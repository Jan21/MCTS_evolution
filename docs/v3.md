# MCTS V3 — Constraint-Context with Deep No-Good Learning

## Overview

V3 adds a **constraint store** and **no-good table** to the MCTS search. Each tree node tracks explicit commitments (which robots must be where), and when conflicts are detected, V3 records **no-goods** — context-specific rules that prevent the same bad decision from being tried again. This gives the search structured memory about which subgoal choices fail and why, rather than relying on cost feedback alone.

## What Changed from V1/V2

V3 shares V1's core MCTS loop and all plan-building helpers. The additions are:

1. **Constraint store** (commitments) on each MCTS node
2. **No-good table** (global, shared across the entire search)
3. **Decision history** for blame attribution
4. **No-good filtering** during expansion and rollout
5. **Dead node detection** and upward propagation
6. **Conflict detection** after each subgoal application

## Key Concepts

### Commitment Objects

Each MCTS node carries a list of commitments describing what its plan requires:

- **`BlockReq(robot_color, position, segment_id, decision_id)`** — a robot must be at a specific position to act as a blocker for a segment. Created when a subgoal's support robot is assigned.

- **`ProtectReq(robot_color, position, segment_id, decision_id)`** — a robot must not be moved. Added lazily when a mover-blocker conflict is detected.

- **`SupportReq(segment_id, choices, chosen, decision_id)`** — a segment needs a helper, with multiple possible `(robot_color, position)` choices. The `chosen` field starts as `None` (lazy) and is set when the candidate concretely specifies a helper.

Each commitment is tagged with the `decision_id` of the expansion step that created it, enabling blame attribution during conflict resolution.

### Context Signatures

A context signature is a hashable summary of the constraint store:

```python
frozenset of (robot_color, position, commitment_type)
# e.g., {("blue", (3, 7), "block"), ("green", (1, 4), "support")}
```

Used for no-good matching: a no-good recorded in context `{A, B}` also applies in context `{A, B, C}` (superset matching — more constraints only makes things harder).

### No-Good Table

The no-good table is a global list of `NoGood(ctx_sig, action)` entries, shared across all MCTS iterations:

- **Recording**: When a conflict is detected, V3 identifies the **culprit decision** (the most recent decision in the conflict set), builds the context signature from all commitments before that decision, and records `(context, culprit_action)` as a no-good.

- **Matching**: Before expanding a child or selecting a rollout action, V3 checks if the action is forbidden by any no-good whose context is a subset of the current context.

- **Subsumption**: If no-good N1's context is a subset of N2's for the same action, N1 is more general and subsumes N2 (N2 is removed). This keeps the table compact.

- **Bounded size**: The table is capped at `max_nogoods` entries (default 500), dropping the oldest when full.

### Conflict Detection

After each subgoal application, V3 checks all commitments for:

1. **Position conflict**: Same robot required at two different positions by different segments.
2. **Resource exhaustion**: A `SupportReq` whose every choice is blocked by other commitments (no feasible helper remains).

When a conflict is found, the culprit decision is identified and a no-good is recorded. The node is still created (not discarded) to avoid over-pruning — but future visits will know to avoid that action in similar contexts.

### Dead Node Propagation

If all children of a node are marked dead (all possible actions filtered by no-goods), the node itself is marked dead. This propagates upward: if all children of a parent are dead, the parent is also dead. Dead nodes are skipped during selection.

### No-Good Filtering

Applied at two points:

- **During expansion**: Candidates matching a no-good for the current node's context are skipped entirely.
- **During rollout**: Candidates are filtered by no-goods. If all candidates are filtered, the filter is relaxed (fall back to unfiltered) to avoid deadlocking the rollout.

## Configuration (`conf/v3.yaml`)

| Parameter           | Default | Description                                          |
|---------------------|---------|------------------------------------------------------|
| `max_iterations`    | 50      | Number of MCTS iterations                            |
| `ucb_exploration`   | 1.41    | Exploration constant (sqrt(2))                       |
| `pw_C`              | 2.0     | Progressive widening coefficient                     |
| `pw_alpha`          | 0.5     | Progressive widening exponent                        |
| `max_rollout_depth` | 30      | Max subgoal insertions per rollout                   |
| `penalty_cost`      | 1000.0  | Cost assigned to failed expansions/rollouts          |
| `max_nogoods`       | 500     | Maximum no-good table size                           |
| `nogood_subsumption`| true    | Enable subsumption pruning of redundant no-goods     |
| `backjump_enabled`  | true    | Enable conflict detection and no-good recording      |

## Trade-offs

**Advantages over V1/V2:**
- Precise blame attribution — only the actual culprit decision is penalized, not the entire subtree
- No-good learning prevents repeating the same mistakes across iterations
- Dead node detection avoids wasting iterations on exhausted subtrees
- Context-specific no-goods distinguish "action X is bad when Y was chosen" from "X is always bad"

**Costs:**
- Additional memory per node (commitment list + decision history)
- No-good matching cost per expansion/rollout step (linear scan of no-good table)
- Context signature design affects precision: too specific → no-goods rarely match; too general → over-pruning
- Conflict detection only catches position conflicts and resource exhaustion; subtler coupling (like ordering dependencies) is not modeled
