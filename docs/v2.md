# MCTS V2 — Lazy-Coupling with Conflict Graph

## Overview

V2 extends V1 by adding a **conflict graph** that tracks helper robot reuse across plan segments. When two segments need the same helper robot at different positions, V2 detects this conflict early and adjusts both candidate scoring and tree exploration accordingly. The goal is to avoid plans that look good in isolation but fall apart due to robot relocation costs.

## What Changed from V1

V2 shares V1's core MCTS loop (select → expand → rollout → backpropagate) and all the plan-building machinery (`_build_initial_plan`, `_apply_subgoal`, `_try_close_edge`, etc.). The differences are:

1. **Footprint tracking** on each MCTS node
2. **Conflict detection** when footprints clash
3. **Soft penalty** on candidate scores during expansion and rollout
4. **Exploration bonus** for nodes with unresolved conflicts
5. **Relocation penalty** added to rollout cost estimates

## Key Concepts

### Footprints

Each MCTS node maintains a `footprints` dictionary mapping plan segments (edge tuples) to the robot positions they require:

```python
footprints: dict[tuple, dict[str, int]]
# e.g., {("bn_3", "sg_1"): {"blue": 42, "green": 17}}
```

When a subgoal is applied, its support robot's `{color: position}` is recorded in the segment's footprint. Footprints are inherited from parent to child and accumulated as the plan grows.

### Conflict Detection

A **helper-reuse conflict** occurs when two segments need the same robot color at different positions. Conflicts are stored as a set of `frozenset({seg1, seg2})` pairs on each node.

```python
# Conflict: blue robot needed at position 42 for seg1, but position 87 for seg2
conflict_edges: {frozenset({("bn_3", "sg_1"), ("bn_5", "sg_2")})}
```

Conflicts propagate upward — when a rollout or expansion discovers a new conflict, it is added to the parent MCTS node as well, ensuring the tree remembers what it has learned.

### Soft Conflict Penalty (Candidate Scoring)

During expansion and rollout, each candidate subgoal receives a penalty based on how much it conflicts with existing footprints:

```
adjusted_score = base_score + sum(relocation_distances for conflicting robots)
```

This biases the search toward subgoals that reuse helpers consistently, without hard-blocking alternatives that might still be globally optimal.

### Exploration Bonus (Selection)

The LCB formula gains an extra term for nodes with conflicts:

```
LCB(child) = avg_cost - C_explore * sqrt(log(N_parent) / N_child) - C_conflict * log(max_component_size)
```

Connected components in the conflict graph determine `max_component_size`. Larger conflict clusters create more uncertainty about true cost, so they get more exploration. This prevents the tree from prematurely committing to plans with unresolved conflicts.

### Relocation Penalty (Rollout Evaluation)

When a rollout produces a complete plan, V2 adds the estimated relocation cost for all conflicting robot positions:

```
rollout_cost = exact_plan_cost + sum(relaxed_distance(pos1, pos2) for each conflict)
```

This gives the backpropagation signal a more realistic cost estimate than V1, which would ignore these hidden costs entirely.

## Trade-offs

**Advantages over V1:**
- Detects helper-reuse conflicts early instead of discovering them at evaluation time
- Conflict-aware candidate scoring steers the search away from problematic subgoals
- Extra exploration of conflicted subtrees prevents premature convergence on infeasible plans
- More accurate rollout cost estimates improve backpropagation quality

**Costs:**
- Additional memory per node (footprints + conflict edges)
- Extra computation per expansion/rollout step (conflict penalty calculation)
- Relocation penalty is a heuristic estimate — actual relocation cost may differ
- Conflict detection is "lazy" (only triggered when subgoals are applied), so some conflicts may be discovered late
