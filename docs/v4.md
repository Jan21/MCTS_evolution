# MCTS V4 — Segment-Node with Context-Signature Transpositions

## Overview

V4 introduces a **two-level node structure** with a **transposition table** that shares subgoal statistics across different plans. Instead of treating each plan as an isolated state, V4 recognizes that the subproblem "move robot R from A to B" recurs across many plans and can be solved once and reused. Coupling between segments is handled through **footprint-based clash penalties** rather than explicit constraints.

## What Changed from V1/V2

V4 shares V1's plan-building helpers but restructures the MCTS nodes:

1. **Plan nodes** (`PlanNode`) hold the partial plan and aggregate footprints — similar to V1's nodes
2. **Segment nodes** (`SegmentNode`) are shared via a transposition table — they accumulate statistics across many different plans
3. **Footprint clash penalties** replace V2's conflict graph
4. **Two-level UCB**: plan-level selects which segment to refine, segment-level selects which subgoal option
5. **Two-level backup**: segment options and plan nodes are updated separately

## Key Concepts

### Segment Nodes and Transposition Table

A segment node represents the subproblem of refining one open edge. It is keyed by a **segment signature**:

```python
(robot_color, start_pos, goal_pos, context_sig)
# context_sig = frozenset of (robot_color, position) for nearby committed robots
```

The `context_sig` captures which robots are frozen in the neighborhood (within `context_neighborhood_radius` Manhattan distance of the segment's endpoints). Two different plans that need the same robot movement in the same local context will share a segment node.

Each segment node holds:
- **Subgoal options**: list of `SubgoalOption` objects, each with the subgoal, its footprint, and per-option MCTS statistics (`visit_count`, `total_cost`)
- **Progressive widening state**: options are expanded lazily from a sorted candidate list

### Footprint Tracking

Each subgoal option records a **footprint** — `{robot_color: position}` for the support and helper robots it uses. Plan nodes aggregate footprints from all selected options.

### Clash Penalties

When selecting a segment option, V4 computes the **footprint clash penalty** against the plan's current aggregate footprint:

```
clash_penalty = sum(relaxed_distance(pos1, pos2))  for each robot at conflicting positions
```

This penalty is added to the UCB exploit term, biasing selection toward options that don't conflict with already-chosen subgoals. If relocation is impossible, the penalty is infinity.

### Pairwise Penalty Table

V4 maintains a global table of `(option_key_i, option_key_j) -> (total_penalty, count)` accumulated during rollouts. This records which pairs of options tend to clash, enabling better selection in future iterations.

### Two-Level Selection

1. **Plan level**: Standard LCB selects which tree node to visit. The highest-cost open edge is chosen for refinement.
2. **Segment level**: UCB1 over the segment node's options, with clash penalty and pairwise penalty added to the exploit term. Unvisited options are prioritized.

If the UCB-selected option has already been tried (or fails `_apply_subgoal`), V4 iterates through all available options in the segment node until one succeeds.

### Two-Level Backup

After a rollout:
1. **Segment level**: Each selected option's `visit_count` and `total_cost` are updated with the rollout cost
2. **Plan level**: Standard backpropagation updates plan node statistics

Segment node visit counts are also incremented during plan-level backpropagation, keeping the segment-level UCB denominators accurate.

## Trade-offs

**Advantages over V1/V2:**
- Strong reuse: "how to move robot A to position P" is learned once and shared across all plans that need it
- Context signatures provide controlled generalization — similar local contexts share statistics
- Footprint clash penalties provide structured coupling information without explicit constraint stores
- Pairwise penalty table enables cross-plan learning about which option combinations are problematic

**Costs:**
- Context signature design is critical — too coarse and the transposition conflates different situations; too fine and reuse drops. On some environments (e.g., envs with many interacting helpers), V4 can produce higher costs than V1-V3
- Segment node candidates are populated from the first plan that creates the node; later plans with the same signature reuse those candidates even if the plan context has shifted
- The transposition table grows with the number of unique segment signatures encountered
- Footprint-based penalties are approximate — they don't capture ordering constraints or non-local coupling
