# Matched-budget comparison: backward subgoal planner vs forward move planner

## Protocol

- **Instances**: the identical set of 450 instances for every system, materialized once by `eval/bench_instances.py` (`eval/data/bench450.jsonl`, sha256 `1b384dfd375c161b...`). Each instance stores the exact move-optimal cost d\* (oracle used only for this reference label, never at inference).
- **Matched budget**: every system runs best-first search capped at **1200 expansions** per instance with **top-k = 5** proposals per expansion (primary operating point). One expansion = one popped node whose children are generated; in both systems this costs exactly one policy pass plus one batched value pass over <= k children, so NN passes per expansion are equivalent. Wall-clock time is reported as a secondary metric.
- **Scoring**: primitive moves. Forward plans are already primitive move sequences. Backward plans are subgoal DAGs realized into moves by `eval/realize.py`; the backward "solved" criterion is STRICT realization success (segments executed in dependency order under full joint-state slide physics). Regret = achieved moves - d\*, over solved instances only.
- **Run**: `PYTHONPATH=. python -m eval.compare --instances eval/data/bench450.jsonl --expansions 1200 --k 5 --skip-backward --device cuda --forward-ckpts move_planner/checkpoints/best.ckpt,move_planner/checkpoints/candidate_scored.ckpt,move_planner_v2/runs_warm/iter5.ckpt,move_planner_v2/runs_scratch_v5/iter15.ckpt --out eval/results/comparison_forward.json --md COMPARISON.md` (2026-07-09T16:52:55). This report is regenerated by every `eval.compare` run; the table reflects the instance file and budget above.

## Search efficiency

The two formulations spend search effort very differently on the same puzzles and the
same budget cap. The subgoal planner completes a plan after a mean of **2.9 expansions**
(0.34 s/puzzle); the move-level planners need **36–424 expansions** (1.0–11.4 s/puzzle)
depending on training. Reading: reasoning over subgoals compresses the search by one to
two orders of magnitude, because one subgoal decision commits several moves at once and
exact distance tables absorb the travel between them. The move-level planners pay for
their move-by-move fidelity with far more search; the subgoal planner pays for its
compression with plans that are not always playable as-is (53.1% strictly executable —
see appendix). Which cost matters more shifts with problem size; the scaling
configurations (more robots, larger boards) measure exactly that trade.

## Result history and the vocabulary ceiling

> **Mechanism corrected in `SOURCE_OF_TRUTH.md` §5.** The ~90% ceiling figure is verified
> (true ceiling 90.7%: 42/450 puzzles have no strictly-playable subgoal plan). But its
> *cause* is not one "no legal plan in the vocabulary" bucket — it splits into 22 puzzles
> where no complete plan can be built and 20 where complete plans exist but none refine
> to legal moves. The taxonomy in `eval/results/residual_failures_postfix.json` predates
> two of the four fixes and does not describe the final state.

The backward rows above are the 2026-07-12 official rerun
(`eval/results/final450_backward_{plain,anytime}.json`) after four verified repairs, none
of which changed the method: a proposal bug that let a robot be scheduled to bounce off
itself; a second proposal bug that let one robot be recruited under two identities; a
completeness gap that accepted plans whose declared stopper was never placed; and two
realizer corrections that execute a plan's own segments in the order its cost model
assumes. Playable-plan rate on the matched first-150 slice moved
54.0% → 63.3% → 74.7% → 79.3% → 80.0% across those steps (files in `eval/results/`,
zero-regression A/B for each realizer change).

A failure taxonomy of everything that remains
(`eval/results/residual_failures_postfix.json`) shows the residue is mostly NOT
trainable or repairable: on the first-150 slice roughly one puzzle in ten has **no legal
plan at all in the subgoal vocabulary** (the plan language cannot express "move this
robot aside and bring it back", and some puzzles have no clean completion once illegal
shortcuts are excluded). The practical ceiling of this plan language on this test set is
therefore about 90%, and the checked row sits essentially on it. Earlier higher-looking
numbers (99.6% historical, 100% plan-found) counted plans that could not be played
legally move-by-move.

2026-07-13 addition (`eval/results/final450_backward_prefix.json`,
`eval/results/prefix_check_ab.json`): checking playability of each plan's already-fixed
steps **as children enter the search** (a pure physics filter, zero false prunes across
the verification set) makes the plain first-plan-returned search reach the same 89.1% —
the planner now refuses to build unplayable plans rather than discarding them afterwards.
The remaining gap to the 90.7% ceiling is proposal coverage (the top-5 beam never
generates the needed candidate), not budget or ranking.

## Appendix: backward planner detail

- Checkpoints: `checkpoints_backward/{policy_v2,value_v2}.ckpt`, retrained 2026-07-09 on regenerated
  self-consistent data (`nn/data/combined_v2.jsonl`, 135,834 records; the original `combined.jsonl`
  is geometry-inconsistent with the current board pkls for env 1000-2999 and was not used).
  Offline value-net test metrics: regret 0.449, MAE 2.17, top1 0.810 (historical reference from the
  original data/boards: 0.356 / 2.07 / 0.827 — statistically consistent given the board regeneration).
- **Plan-found vs strict-executable**: the backward search produced a complete subgoal plan for
  **450/450 instances at a mean of 2.9 expansions** (it needs almost none of the 1200-expansion
  budget). 211 of those plans fail STRICT legal realization — the plan's segments are blocked by
  robots the abstraction assumes away (blocker-clearing). The 53.1% headline is therefore an
  executability gap, not a search failure; the realizer is a direct topological executor with no
  repair/replanning. Mean abstract plan cost 7.15; 65 plans have negative abstract regret
  (impossible-as-played shortcuts), confirming abstract counts must not be compared to d*.
- The abstract count sums each plan segment simulated with only its intended support robot on the board (blocker-clearing model). It can under-count true game moves, so regret computed from it can be negative; the strict count is the fair, legal-execution figure and is what the main table reports.
- Historical note: the original backward system's documented 99.6% "solved" corresponds to the
  plan-found criterion in its own weighted-cost units, not to legal move-level execution.

## Footnotes

1. **Expansion granularity**: one backward expansion commits an entire subgoal (a multi-move commitment: mover approach plus helper placement), while one forward expansion commits a single primitive move. A shared expansion cap therefore grants the backward planner strictly more solution-building work per expansion; the matched budget is generous to the backward system (the conservative direction for the comparison).
2. **Environment model**: the backward planner's environment includes precomputed exact shortest-path distance tables per board (used for exact-fix checks and edge costs at inference). The forward planner uses only the wall geometry at inference.
3. Checkpoints, budgets, timestamps and the full per-instance rows are recorded in
   `eval/results/comparison_forward.json` (forward systems, 2026-07-09T16:52) and
   `eval/results/comparison_backward.json` (backward system, 2026-07-09T23:52); both consumed
   the identical `eval/data/bench450.jsonl` (sha256 `1b384dfd375c161b...`).
